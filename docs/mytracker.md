# VK MyTracker

Веб-счётчик MyTracker стоит рядом с Яндекс Метрикой и получает **те же
цели с теми же названиями**: обе системы вызываются из одного места,
`miniapp/src/metrika.ts` (`ymHit`, `ymReachGoal`). Новая цель, добавленная
через `ymReachGoal`, автоматически уходит в оба счётчика.

Счётчик покрывает все площадки, потому что все они — один и тот же веб-код:
Telegram Mini App, сайт, установленное приложение (PWA и TWA из RuStore).

## Включение

ID счётчика впечатывается в бандл на этапе сборки:

```ini
# .env прода
VITE_MYTRACKER_ID=1234567
```

```bash
docker compose up -d --build miniapp
```

Пустое значение — MyTracker выключен целиком: скрипт не грузится, события
не копятся. Поэтому на тесте ID не задаём, чтобы не мусорить в боевом проекте.

## Что отправляется

- **pageView** — при открытии и на виртуальных переходах: `/landing`,
  `/level`, `/schools`, `/subscribe`, `/subscribe/thanks`.
- **setUserID** — id аккаунта, один раз после входа. Один человек с
  телефона и ноутбука считается одним пользователем.
- **reachGoal** — цели ниже. В каждой есть параметр `platform`:
  `telegram`, `app` (установленное приложение) или `web`. Остальные
  параметры те же, что в Метрике.
- **Выручка**: у `subscription_paid` сумма `amount_rub` дополнительно
  передаётся как `value`.

## Веб-цели в интерфейсе MyTracker

События из кода приходят сами, создавать их заранее не нужно: они
появляются в отчётах по событиям после первой отправки. Чтобы
использовать событие как конверсию (например, для оптимизации рекламы
VK Ads для сайта), в настройках проекта MyTracker заводится цель с **тем же
названием**, что в таблице. Минимальный набор для рекламы:
`landing_cta_click`, `level_landing_claimed`, `session_started`,
`subscribe_plan_clicked`, `subscription_paid`.

## Android-приложение: регистрация, начало занятия, оплата → VK Ads

Если установки уже видны, SDK работает. Следующий необходимый шаг —
передавать **события именно Android-приложения** с тем же `instanceId`,
который выдал SDK. Параметр `platform=app` у веб-цели сам по себе не
превращает её в мобильное событие и не привязывает к рекламной установке.
`VITE_MYTRACKER_ID` относится к веб-счётчику; для этой воронки его наличие
не обязательно.

| Действие | Мобильное событие MyTracker | Когда фиксируется |
|---|---|---|
| Регистрация | стандартное `registration` | Первая связка аккаунта и установки; аккаунт создан не более двух часов назад. Для старого аккаунта отправляется `login`. |
| Начало занятия | custom event `session_started` | Backend создал запись занятия: voice, chat, grammar, listening или srs. Для listening это успешная генерация эпизода, а не измерение его прослушивания. |
| Успешная оплата | `customRevenue` + custom event `subscription_paid` | Подтверждённый платёж за личную подписку зачислен пользователю. Сумма и валюта приходят с сервера. |

В `session_started` есть строковые параметры `mode`, `session_id`,
`platform=app`; в `subscription_paid` — `plan`, `amount_rub`, `days`,
`payment_id`, `platform=app`. `customRevenue` содержит `currency=RUB`,
числовую сумму и стабильный `idTransaction=yk-<payment_id>`.
Для оплаты используется последняя известная установка аккаунта — как и
в прежней интеграции. Это включает последующие оплаты этого аккаунта через
сайт; не следует считать такую связь доказательством, что checkout был
открыт именно на этом телефоне.

```text
SDK в APK → стартовый URL ?mt_iid=<instanceId>
                    ↓
Веб-приложение: captureInstallId → локальная память
                    ↓
JWT-вход → POST /api/analytics/mt-install
Занятие → X-MyTracker-Instance-ID (HTTP) / mt_iid (WebSocket)
                    ↓
Backend: mytracker_installs + mytracker_events (очередь)
                    ↓
S2S: registration / customEvent / customRevenue
                    ↓
Android-приложение в MyTracker → настроенная передача событий в VK Ads
```

Установку привязываем к пользователю только после авторизации. Начало занятия
может создать связку само, если первый запрос привязки ещё не успел завершиться.
Обычный браузер не добавляет сохранённый Android-ID к занятиям. На каждом
входе обновляется `last_seen_at`; старый вечный маркер `et_mt_iid_sent` больше
не препятствует запросу.

### Что обновить на сервере

1. GitHub Actions отключён; текущий production обновляется вручную.
   Получить изменения из `main`, затем **до** обновления backend применить миграцию:
   ```bash
   mysql -u megotim4y2 -p megotim4y2 < db/migrations/0041_mytracker_events.sql
   ```
   Миграция `0038_mytracker_installs.sql` тоже должна быть применена.
   SQL-миграции проекта применяются вручную. Полный порядок — в
   [инструкции деплоя](mytracker-deploy.md).
2. Использовать уже заданные `MYTRACKER_APP_ID` и `MYTRACKER_S2S_TOKEN`.
   ID должен принадлежать Android-приложению с пакетом
   `ru.krichigindocs.englishbot.twa`, а токен — давать S2S-доступ к нему.
   Это не ID веб-счётчика, не ID рекламного кабинета и не SDK-ключ из APK.
   Значения ключей не выводить в терминал и не присылать в чат.
3. Обновить backend и miniapp из версии с этими изменениями:
   ```bash
   docker compose up -d --build backend miniapp
   ```
4. Проверить диагностику, используя токен админки из окружения контейнера:
   ```bash
   docker compose exec -T backend python - <<'PY_STATUS'
   import json
   import urllib.request
   from app.config import settings
   req = urllib.request.Request(
       "http://127.0.0.1:8000/api/analytics/mt-status",
       headers={"X-Admin-Token": settings.ADMIN_TOKEN or ""},
   )
   with urllib.request.urlopen(req, timeout=10) as response:
       print(json.dumps(json.load(response), ensure_ascii=False, indent=2))
   PY_STATUS
   ```
   Ответ содержит только статус и счётчики:
   - `tracking_enabled`: ID и токен заданы; это ещё не проверка прав токена;
   - `app_id`: выбранный числовой ID Android-приложения;
   - `linked_installs`: число связок аккаунта и установки;
   - `pending`: события, ожидающие отправки;
   - `accepted`: запросы, на которые S2S API ответил 2xx;
   - `retrying`: ожидающие события с неудачными попытками.

### Проверить актуальный APK

Если `linked_installs=0` после входа из приложения, сначала проверить передачу
`mt_iid`: SDK может считать установки, даже когда APK не передаёт этот ID
в веб-часть. Нужен **реальный UUID из `MyTracker.getInstanceId`**, не рекламный
идентификатор и не придуманная строка.

В проекте Bubblewrap применить существующий скрипт и собрать новую версию,
если текущий APK не содержит этой связки:

```bash
python3 /path/to/englishbot/scripts/twa_mytracker_patch.py . <SDK_KEY>
bubblewrap build
```

При новой версии: поднять `appVersionCode` → `bubblewrap update` → скрипт →
`bubblewrap build`. Если актуальный APK уже передаёт `mt_iid`, для изменений
в backend и веб-части повторная сборка APK не требуется.

### Проверка в MyTracker и VK Ads

1. В MyTracker выбрать **Android-приложение**, соответствующее SDK и
   `MYTRACKER_APP_ID`. Проверить связь с нужным рекламным кабинетом VK Ads
   и разрешённую передачу/postback нужных событий. Веб-цели из раздела выше
   относятся к другой воронке.
2. На тестовом телефоне открыть приложение, зарегистрировать **новый**
   аккаунт и начать занятие. Проверить `registration` и `session_started`
   в мобильных отчётах MyTracker. Вход старого аккаунта даст `login`.
3. Для оплаты проверить подтверждённую успешную транзакцию. Проверка кода
   с mock-сервером доказывает формат и доставку очереди, но не создаёт события
   в реальном рекламном кабинете. Не отправлять вымышленные оплаты в боевой
   MyTracker ради появления события в списке.
4. Когда события появились в мобильных отчётах, проверить их передачу в
   VK Ads и доступность в списке событий **этого приложения**. Для выбранной
   воронки нужны регистрация, custom event `session_started` и оплата
   (`subscription_paid` либо соответствующее событие выручки).
   Для оптимизации по покупке выбирайте одну конверсию: не суммируйте
   `customRevenue` и `subscription_paid` как две отдельные покупки.

Названия и расположение разделов кабинетов могут меняться. Если событие
есть в MyTracker, а в VK Ads отсутствует, проверяется интеграция/postback,
права и привязка приложения в кабинетах; добавление ещё одной веб-цели
эту проблему не решает. Поступление в отчёты и передача в VK Ads асинхронны.
Успешный HTTP-ответ S2S сам по себе не доказывает, что обработка в обеих
системах завершилась.

### Если событие не пришло

- `tracking_enabled=false`: проверить имена переменных и **перезапуск**
  backend после изменения `.env`.
- Нет связок установки после входа: проверить APK, `mt_iid`, регистрацию
  native-ID и ответы `POST /api/analytics/mt-install`. `401` — нет JWT,
  `422` — ID не является UUID; `500` — смотреть миграции и журнал.
- Есть `pending`/`retrying`: в `docker compose logs backend` искать
  `[mytracker] method=... HTTP=...` или `transport=...`.
  `401/403` — проверить S2S-ключ и права на Android-приложение;
  ошибки соединения — доступ сервера к `tracker-s2s.my.com` по HTTPS;
  `delivery queue failed` — в том числе миграцию 0041.
- `accepted` растёт, но нет события в нужном приложении: сверить `app_id`,
  отчёт Android-приложения и идентификатор установки.
- Есть событие в MyTracker, но нет в VK Ads: проверить передачу этого
  события, выбранный рекламный кабинет и Android-приложение.

### Гарантии и границы доставки

Очередь записывается в той же SQL-транзакции, что связка, занятие или
зачисление оплаты. При ошибке аналитики занятие и доступ к подписке
сохраняют работоспособность, а журнал сообщает о проблеме постановки в очередь.
Фоновый процесс запускается вместе с backend, повторяет неудачные запросы
с увеличением интервала до часа и продолжает после перезапуска.
Регистрация, начало занятия, выручка и custom event оплаты имеют отдельные
стабильные ключи. Успешная часть оплаты не пересылается при отказе второй.
Секреты не записываются в payload или журнал ответов.

Если удалённый сервис принял запрос, но подтверждение потерялось в сети,
повторная доставка custom event возможна. Абсолютная exactly-once доставка
для API без подтверждённого механизма идемпотентности не обещается.

Связки и платежи, созданные **до** этой очереди, не содержат достоверной
истории доставки. Исторические регистрации/оплаты не пересылаются автоматически.
Проверять новую воронку следует новым действием. Это не восстановление
старых рекламных конверсий.

### Локальные проверки разработчика

```bash
# Из корня репозитория, после npm ci в miniapp:
node --test scripts/test_mytracker_frontend.cjs
# БД должна быть локальной, отдельной и оканчиваться на _test; применить миграции.
PYTHONPATH=backend TEST_DATABASE_URL='<local mysql+asyncmy URL to *_test>' \
  /path/to/backend-venv/bin/python -m unittest discover -s backend/tests -v
cd miniapp && npm run build
```

В тестах S2S-сеть заменена mock-транспортом; реальные рекламные события
не отправляются. Официальный клиент с примерами формата запросов:
[tracker-my-com/s2s-api](https://github.com/tracker-my-com/s2s-api).

Проверено в облачной среде: 14 backend-тестов на отдельной MySQL 8.0.46,
8 frontend-тестов, стандартная production-сборка Mini App и локальные
HTTP/браузерные smoke-проверки. Полная проверка TypeScript Mini App
по-прежнему сообщает о 19 существовавших до этих изменений ошибках;
стандартный npm run build их не обнаруживает. Доставка в реальный
MyTracker и кабинет VK Ads этой локальной проверкой не подтверждена.
